## 快速分诊表

| 现象 | 首查位置 | 对应失效模式 |
|---|---|---|
| 崩溃栈落在加锁、解锁附近，线程为 ffrt 工作线程 | 崩溃点锁的声明类型 | 「锁类型错配」 |
| 服务挂起，事件不再处理 | 持锁区间内的被调函数 | 「非递归锁重入」 |
| 插卡、换卡、NV 更新后 IMS 开关状态不对 | 延迟动作标志的消费点 | 「延迟动作在前提满足前执行」 |
| 重复上报时某个配置动作不执行 | 函数中的提前返回 | 「提前返回跳过逻辑」 |
| 来电不报、挂断后界面残留 | `ReportCallsData` 的三类分支 | 「连接表对比遗漏」 |
| 状态变化日志正常但 call_manager 未收到 | `callManagerCallBack_` | 「回报出口为空」 |
| IMS 服务重启后 VoLTE 不可用 | `ImsCallClient` 重连与开关同步 | 「重连后未恢复状态」 |
| 某卡的配置影响了另一张卡 | static map 的卡槽键 | 「跨卡槽共享状态」 |
| 未加载扩展库的产品崩溃 | `TELEPHONY_EXT_WRAPPER` 调用点 | 「钩子空指针」 |
| 两个部件单独升级后接口行为错乱 | 接口码与读写顺序 | 「跨仓定义不同步」 |

## 失效模式

### 锁类型错配

**机制：** 在 ffrt 工作线程上执行的代码使用 `std::mutex`，或同一份数据被不同类型的锁保护。阻塞的 `std::mutex` 占住工作线程，与 ffrt 调度冲突，表现为偶发崩溃或挂起，栈停在锁操作附近。

**识别：** 崩溃栈顶是 `lock`、`unlock`、`lock_guard` 构造或析构；所在类的其他锁已是 ffrt 类型；仓内历史提交有同类改动。

**修复：** 把该锁改为 `ffrt::mutex`（需要递归时 `ffrt::recursive_mutex`），同步修改头文件声明、cpp 定义与全部加锁点的模板参数。**不要**先去给读点补锁。

### 非递归锁重入

**机制：** 持有 `operatorMutex_` 的函数调用了内部再次获取 `operatorMutex_` 的函数。

**修复：** 拆出不加锁的内部实现供持锁调用方使用，或先在锁外取得所需值。

### 延迟动作在前提满足前执行

**机制：** 标志在卡事件中置位，在网络事件中被消费；消费时没有判断网络是否已注册，动作过早执行得到无效结果，并清除了标志，后续真正满足前提时不再执行。

**识别：** 问题只在插卡、换卡、NV 更新之后的一段时间出现；modem 查询结果与最终状态不一致。

**修复：** 在消费条件中加入全部前提，前提不成立时保留标志；确认消费点位于提前返回之前或不受其影响。

### 提前返回跳过逻辑

**机制：** 「状态未变化则返回」的分支之后放置了每次事件都需要执行的逻辑。

**修复：** 把与状态变化无关的逻辑移到提前返回之前，并确认锁范围仍然正确。

### 连接表对比遗漏

**机制：** `ReportCallsData` 对比上报列表与 `connectionMap_` 时，只处理了新增或更新，没有处理「本地有、上报无」的挂断，或反之。

**修复：** 三类情形都要覆盖；对比在 `connectionMapMutex_` 内完成。

### 回报出口为空

**机制：** call_manager 尚未注册或已退出，`callManagerCallBack_` 为空，回报被丢弃。

**修复：** 这是设计行为，修复点通常在 call_manager 的注册时序；本仓只需保证日志与打点。

### 重连后未恢复状态

**机制：** IMS 服务重启后 `ImsCallClient` 重连成功，但开关、能力等状态没有重新下发。

**修复：** 在重连回调中补充状态同步，并确认同步动作的前提（卡、网络）成立。

### 跨卡槽共享状态

**机制：** `CellularCallConfig` 的 static 成员对两张卡共享，按卡槽键区分；遗漏卡槽键或卡槽号未校验时，一张卡的配置写入另一张卡。

**修复：** 读写前校验卡槽号，所有 per-slot 数据以卡槽为键。

### 钩子空指针

**修复：** 调用 `TELEPHONY_EXT_WRAPPER` 函数指针前判空，空时走默认逻辑。

### 跨仓定义不同步

**修复：** 接口码只追加，代理写入与 Stub 读取顺序一致，两仓同步提交。

## 根因排查方法

- **先确认锁的声明类型，再判断锁的覆盖范围。** 栈在锁附近时，锁类型错配比漏锁更常见于本仓。
- **从置位追到清位。** 标志类问题逐一列出置位、读取、清位点，再对照事件到达顺序推演。
- **一个现象对应一条机制。** 候选根因必须能解释现象中的触发条件与表现；解释不了的代码瑕疵记为技术债，不作为结论，也不在本次改动中一并修改。
- **查仓内历史。** `git log -S <符号名>` 查同一符号的历史改动，本仓锁类型与配置时序有多次同类修复。

## 修复反例

| 反例 | 问题 | 正确做法 |
|---|---|---|
| 崩溃在锁附近，就给所有读点补 `std::mutex` 保护 | 放大了错误类型的锁，引入重入死锁 | 先改锁类型，再评估是否确有漏锁 |
| 只改 `lock_guard` 模板参数，不改头文件声明 | 编译失败 | 声明、定义、全部加锁点一起改 |
| 前提不满足时仍清除延迟标志 | 动作永久丢失 | 前提成立才清位 |
| 为规避事件顺序，在卡事件里直接执行需要网络的动作 | 顺序不固定，仍会失败 | 在每个前提满足的事件中检查 |
| 在 Control 中直接调用 call_manager 回调 | 绕过唯一出口 | 经 `CellularCallRegister` |
